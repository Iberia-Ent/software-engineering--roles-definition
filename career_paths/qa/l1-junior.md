# QA Engineer · L1 Junior

[Academy index](../README.md) · [QA overview](./README.md)

## Purpose

Explain how a Junior QA Engineer contributes to product quality, what support the team should
provide, and which observable behaviours indicate progress.

## Audience

Product Owner, Product Manager, Delivery Lead, and Technical Lead. QA Manager, QA Engineer,
Coach, and Mentor use the linked criteria for discipline-specific review.

## Overview

L1 develops QA fundamentals and disciplined execution with guidance. The November matrix expects
basic knowledge across the competencies, including performance, accessibility, cloud awareness,
and observability. This is a learning and supported-contribution level, not independent
ownership of a squad's quality decisions.

## Product-team context

For example, the QA Engineer may execute an agreed test scope for a familiar user story, record
results, and report a defect with enough evidence for the team to act. Stakeholders should
explain the business purpose and critical flows, and arrange access to an experienced QA
reviewer. Ambiguous results should prompt a question, not an unsupported pass or fail.

Reliable reporting is more important than simply increasing the number of cases executed. The
person should make blockers visible, follow approved practices, and learn why a test matters. AI
use must remain within the source's supervision constraints; faster output is not evidence that
the underlying QA judgement is sound.

## Evidence stakeholders can discuss

Useful evidence includes a clear defect report, an accurate execution record, a promptly raised
blocker, and an explanation of what a test was intended to protect. Discuss how much guidance
was needed and what learning was retained. These examples support review without adding new
promotion thresholds.

### Performance Testing
<a id="detail-l1-performance-testing"></a>

[Exact source criteria](./qa-career-path.md#criteria-performance-testing-l1-junior-foundation-basic-knowledge)

**Level snapshot:** Knows concepts and test types, flags performance impact

Relate scenarios and results to expected product usage, response-time objectives, and customer

### Accessibility (A11y)
<a id="detail-l1-accessibility-a11y"></a>

[Exact source criteria](./qa-career-path.md#criteria-accessibility-a11y-l1-junior-foundation-basic-knowledge)

**Level snapshot:** Knows WCAG basics and which stories need A11y

Connect checks to the people and journeys the product must support, and to the applicable
compliance evidence. Automated findings are useful but do not replace the manual checks
described by the source.

- [Understands why accessibility matters and the EU accessibility legal context](./qa-career-path.md#qa-item-l1-accessibility-a11y-01)
- [Knows WCAG 2.2 AA principles (POUR) and the trigger (pulsador) model](./qa-career-path.md#qa-item-l1-accessibility-a11y-02)
- [Knows which stories require A11y validation: any customer-facing front, new or legacy](./qa-career-path.md#qa-item-l1-accessibility-a11y-03)
- [Runs basic manual checks: keyboard, focus, contrast, alt text, labels](./qa-career-path.md#qa-item-l1-accessibility-a11y-04)
- [Executes A11y Gherkin tests from Xray Test Sets with guidance](./qa-career-path.md#qa-item-l1-accessibility-a11y-05)

### AWS & Cloud Awareness
<a id="detail-l1-aws-cloud-awareness"></a>

[Exact source criteria](./qa-career-path.md#criteria-aws-cloud-awareness-l1-junior-foundation-basic-knowledge)

**Level snapshot:** Knows basic cloud and AWS vocabulary

Use cloud knowledge to identify how architecture, environment differences, or asynchronous flows
change test scope. QA is expected to collaborate with specialists, not replace Cloud or
Architecture implementation ownership.
