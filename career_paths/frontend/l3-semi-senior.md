# Frontend Developer · L3 Semi-Senior

[Academy index](../README.md) · [Frontend overview](./README.md)

## Purpose

Explain the delivery judgement and ownership expected at L3, with direct references to the
technical and behavioural criteria used in assessment.

## Audience

Product Owner, Product Manager, Delivery Lead, and Technical Lead. Frontend Developer, Coach,
and Mentor review technical evidence against the chapter.

## Overview

L3 deepens design, architecture, and quality judgement in the assigned track. The source
combines advanced technical criteria with communication, flexibility, urgency, and ownership.

The person should be able to explain choices and carry work through to completion without
the lead having to chase status. This does not remove review or collaboration; it changes the
expectation from following the work to actively owning its progress and implications.

## Product-team context

An illustrative assignment is a customer-facing feature that combines state management, API
consumption, and accessible interactions. The Developer should clarify how the solution supports
the user journey and what quality risks remain.

Technical depth should make the delivery easier to reason about, not make the implementation
harder for the team to maintain. Product stakeholders should receive an understandable
explanation of the options, constraints, and consequences rather than only implementation
terminology.

When scope changes or time pressure increases, stakeholders should continue receiving clear
updates and realistic alternatives. Ownership does not mean hiding difficulties or avoiding
technical review. It means keeping responsibility for moving the work forward and involving
others when their input is needed.

## Evidence stakeholders can discuss

Review a decision the Developer explained, a feature taken from clarification through delivery,
and an occasion when priorities or requirements changed.

Pair those observations with technical evidence such as tests, accessibility audits, and
implementation review. This connects product impact with demonstrated competence instead of
relying on confidence in meetings.

Discuss whether the behaviour is sustained across work. A larger task or a successful release
is useful context, but neither establishes the level without evidence of the associated
judgement, collaboration, and technical capability.

## Detailed criteria

The criteria below reproduce the level-specific expectations in the English source chapter.
The accompanying interpretation explains their relevance to product delivery; it does not add
a separate promotion threshold.

### Common technical criteria — both tracks

<a id="detail-l3-common"></a>

[Source criteria](./Frontend_Career_Path_Chapter.md#criteria-l3-common-technical-criteria-both-tracks)

For a feature spanning frontend behaviour and APIs, assess whether the Developer can explain
type and state boundaries, choose patterns that reduce coupling, document the API contract,
and maintain automated quality checks.

Discuss the trade-offs and follow-up risks, not just framework fluency. A design pattern is
valuable when it helps the team understand, change, or verify the solution; naming several
patterns is not equivalent to applying them appropriately.
